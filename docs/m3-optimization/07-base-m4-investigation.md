# Base M4 community performance investigation

Evidence reviewed through 2026-11-07 for the Switch 2 remake (title ID `0400486024DEC000`). The primary repository is [seedds/nxnative](https://github.com/seedds/nxnative). Public reports substantiate **39.5–41.6 FPS on specific outdoor routes and 44.9–45.2 FPS inside Link's house on base M4 / 24 GB**. The closest earlier run on the same reporter's hardware and save was **34.7 FPS inside the house**. No public result reviewed establishes a matched 20 → 40–45 FPS jump, sustained 60 FPS in Kokiri Village on base M4, or a corresponding gain on base M3 in either target mode. This was a source and evidence review; no new game run was made.

The public bases, source commits and PR refs above identify the components, but the PucaVaz reports did not publish final integration SHAs, individual PR snapshots or binary hashes. The current PR heads may differ from what was tested. The 34.7 FPS post calls its baseline the #1360 build; the same reporter separately names the earlier `574a38f0` build in the PR thread, but the FPS post does not restate its SHA. On the newer stack the reporter also measured [about 28 FPS at the foot of the ladder](https://github.com/seedds/nxnative/issues/1326#issuecomment-6682561324), versus 39–45 on the balcony. Camera and route matter within the village. Treat the stack as a recipe for source review, not an exact benchmark artifact. The near-20 to 40–45 claim could conflate different memory capacities, scenes, counters or builds. Public GitHub reports and indexed press/community coverage did not resolve that missing matched comparison.

### Pro, Max and movie results

- **M4 Pro / 48 GB:** [PaulEins](https://github.com/seedds/nxnative/issues/1265#issuecomment-6675361806) used stan69b/nxnative:`oot-clean` at [`6c71e575`](https://github.com/stan69b/nxnative/commit/6c71e575) plus #1345, #1332, #1350, #1343 and #1376 (chain `ba403debcc6c`, v131072); later changes were added locally. Reported windowed Kokiri Village at 37–56 FPS Docked and 44–60 Handheld, and 60 in the Deku Tree. An [earlier build on the same Pro](https://github.com/seedds/nxnative/issues/1265#issuecomment-6671881847), `oot-clean` `18a9c1a` plus #1345 and #1332 (chain `cd1da67c132d`), reported 28–41 FPS in the forest with substantially higher memory use; multiple changes separate those reports. Exact dimensions and cap are not given for those windows. A [later Docked session](https://github.com/seedds/nxnative/issues/1265#issuecomment-6701492365) used `main` `0c7e88b9` plus six PRs, MetalFX, Standard presentation upscaling and submission timestamps; the reported 1536 × 864 internal size and multi-hour run describe that later stack.
- **M4 Pro / 24 GB:** [LucyferDev](https://github.com/seedds/nxnative/issues/1265#issuecomment-6675590610) used `main` `865cc35f` + `ee9b7765` from #1299 and eight more fixes (the comment lists each head), chain `f7373a425792`, v131072. Default Handheld, internal disk and Metal HUD; dimensions and cap unreported. ~57 FPS describes the title and 47–60 the in-engine opening. The GPU hung before controllable gameplay. Matching the 24 GB memory figure alone misclassifies this machine.
- **M4 Max / 64 GB, 40-core GPU:** [tschope's corrected report](https://github.com/seedds/nxnative/issues/1477#issuecomment-6685270091) on `main` `671c68e139ec` (chain `adec7d81d970`, v131072) shows 60 FPS at the **title** after a pipeline compile stall, windowed with the game's upscaler and bilinear presentation. The [setup](https://github.com/seedds/nxnative/issues/1477#issuecomment-6684325040) names a 2560 × 1440 external display at 165 Hz, 120 Hz fullscreen; it does not establish a 2560 × 1440 drawable in the corrected window or a village rate. [yoBoss283's M4 Max report](https://github.com/seedds/nxnative/issues/1566#issuecomment-6701607347) identifies `main` `b2d46b86` + #1544 at `1b742d462cbb` (chain `5c852d7989ac`), defaults except rumble off, but documents terrain and memory over a long route rather than a controlled FPS benchmark.
- **Other headline numbers:** ChiefSZ13's [#1299 ~60 FPS](https://github.com/seedds/nxnative/pull/1299) is a **base M5 / 24 GB**, v0, windowed 2560 × 1440, Link's house, pre-rebase chain `50b4361afcb0`. The separate [base M4 Air 35.5 → 48.7 FPS result](https://github.com/seedds/nxnative/pull/1456) is the **title movie** with an 8-core GPU, on `main` + #1299/#1300/#1312; the report does not give memory capacity, mode or display size for that measurement. Neither is a base M4 village benchmark.

## What changed, and what our fork already has

Compared the report revisions and patches against `m-gnr/kid-with-sword-remake:perf/apple-m3-oot-docked` at `f9f2efed1baac188982225f5126075b03c20ff9f` (runtime tree `e9c2f7e1f19a8c74e90283e892b8973173eabd61`, chain `dc815e0f38ca`). The common ancestor with `75c1a8cf` is `865cc35fad7034d17c2190f8ce349f61f5bcaba1`; commit ancestry and implementation are distinct because the fork independently ported several fixes. The local [game profile](../../dm/games/0400486024DEC000/game.tsv), [Metal replay](../../dm/gfx/nvn/nvn_mtl.m) and [benchmark record](04-benchmarks.md#ordinary-dispatch-overlap-ab) establish the source and the measured artifact separately.

| Change and evidence | Fork comparison and likely effect |
| --- | --- |
| **Bindless descriptors and view lifetime.** In the M5 bring-up, the [#1299 table and ghost-ring fix](https://github.com/ChiefSZ13/nxnative/commit/6516feb86bd1ec0284c7dc6a7fbc36bb15e63edd) cut submit + present from ~45 to 5–8 ms, with similar GPU times. Later [#1489](https://github.com/seedds/nxnative/pull/1489) ports TheekshanaA/nxnative:`oot-pool-table-notes` ([`95797683`](https://github.com/TheekshanaA/nxnative/commit/9579768396fca25ce0741da47c2810edbefddb08), [`9d486f88`](https://github.com/TheekshanaA/nxnative/commit/9d486f882f77cdfef92dfc459462308b6209639e)); upstream landed [`0c7e88b9`](https://github.com/seedds/nxnative/commit/0c7e88b92b5fdf0dfa0e9496df5652f350f05e20). In four alternating base M4 / 24 GB runs (Handheld, upscale 2.0, `88c7e03f` vs the PR, same app fixture and chain), submit CPU fell ~12–15 → 3–5 ms, house p99 ~35–41 → 24–26 ms and >50 ms balcony frames 23/48 → 3/2. It lacks the complete upstream `REG_POOL`/dead-ID and next-submission transient-ID logic. This is evidence for better tail latency when whole-table walks still occur, with no measured median FPS gain in the M4 A/B. |
| **Depth feedback and segmentation.** Upstream [`6121fd75`](https://github.com/seedds/nxnative/commit/6121fd75312cb4d1af404a01921d437741fea91e), in PucaVaz's newer base, narrows pool depth readers via observed texture IDs and preserves GPU timestamp boundaries while skipping unnecessary busy commits. The upstream `pool_ds_read` feedback set and busy-commit condition are absent. They address different residual costs and have different hazards: first unseen readers in one case, copy visibility and dynamic-resolution timestamps in the other. |
| **Memory headroom and correct content.** The dynamic raw table avoids missing ranges and one GPU hang; #1455 drops stale shared textures, #1453 aliases transient targets (only ~1% residency saving in the newer fixed scene), #1332 handles revoked GPU access, and #1446 guards null getters. The fork opens archive URLs directly; it lacks upstream's private Foundation mapping hook. Use internal archive storage as a configuration experiment. Do not import the private hook or inherit a 14 GB guard, larger alias region or texture release policy from a different stack without local evidence. |
| **Shader cost.** [#1464](https://github.com/seedds/nxnative/pull/1464) caches the last raw range per invocation. The author measured 17.0 → 14.1 ms GPU p50 on **M5 Pro**; sofarx adapted it, without a separate base M4 A/B. [`bd9f422`](https://github.com/seedds/nxnative/commit/bd9f422d613faaba556c63734be0284a9994334a) cuts title NDVE compute by ~7.8 ms on base M4 by keeping HMMA operands in SIMD-group matrices. [#1544](https://github.com/seedds/nxnative/pull/1544) fixes its accumulator collision in the game upscaler. F2IP/float and image atomics, terrain uploads and live-input fixes affect what is drawn; missing work can make a broken image faster. | Fork already has a related last-entry implementation (`185687c5`), and the #1300/#1312 and LDSM correctness work is present. HMMA chains and the merged [native subword-store fix](https://github.com/seedds/nxnative/commit/ffebfd59342514d4fe947f140dd7b0844729cd92) are absent. Our build already selects the plain movie player via a build-gated cut. Neither the title optimization nor the M3 Pro AND/OR foliage experiment explains the cited base M4 village rates. |
| **Scaling and simulation.** [#1459](https://github.com/seedds/nxnative/pull/1459) recognizes NDSR VR variants and their linear colour path for MetalFX. The matched M4 settings report gives little evidence of a large gain from the scaler, drawable size or reduced 3D size on that route. The `oot-mac` frame-delta patch changes simulation time at low FPS. [Frame buffering on an earlier base M4](https://github.com/seedds/nxnative/issues/1265#issuecomment-6668912474) also changed display discards at similar host frame time. | Fork has its own NDSR chain and multiple terminal keys (`83dc6523`), separate present scaling, and the build-gated whole-vsync frame controller (`2de238f3`). Phase Two still observed fallback to native NDSR on the measured artifact. Verify the effective scaler rather than assuming the launch setting took effect. The fork enables present snapshots in this profile; measure actual presents and game speed separately before considering a timing backport. |

The most plausible explanation for the reported same-save gain is a combination of renderer and memory changes, especially less conservative pass splitting and less CPU/residency work, with a different build and test configuration contributing uncertainty. Several individual changes have good evidence for a particular bottleneck on a named machine. None isolates the base M4 outdoor gain, and none can be added arithmetically to the base M3 results. See the [Phase Three technical report](08-phase-three-technical-report.md) for the order of experiments and backport gates.
